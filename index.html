LIVE BUILD04 / 52

Live build: one prompt

Build Subway Surfers.

First use the prompt-engineer skill to improve this prompt. Then write a custom Atomic workflow that does the whole job, and run it.

The workflow generates concept art for the runner, the inspector and his dog, the subway trains, barriers, coins, power-ups, and a neon futuristic city around the tracks with GPT Image 2.5 Flare (gpt-image-2.5-flare), called directly through the OpenAI Images API with the OpenAI API key saved in Atomic. Turn each image into a 3D model with Hunyuan3D-2.1 on Hugging Face, using the Hugging Face token saved in Atomic, clean up and render the models in Blender, rig the runner with a motion-captured run, and build the game with those assets. The game is an endless three-lane run along subway tracks where you switch lanes, jump, and roll past trains and barriers, collect coins, pick up a jetpack, super sneakers, a coin magnet, and a score multiplier, and get caught by the inspector when you crash. Speed increases over time, and the game keeps a score and a high score.

Make it physical: the runner really runs, with arms and legs alternating and feet planted on the track, jumps on a gravity arc, and rolls on the ground. Models sit on the track with shadows under them, collisions match the models, and a crash knocks the runner back before game over. The camera sits low and close behind the runner, like Subway Surfers, and keeps them in view, including beside trains and in the air.

Open the game on my screen while it builds, at 60 fps. Only show changes that pass their checks. The H key hides the developer panels.

Four terms

Test engineering
Designing the checks, not only writing tests.
Verification
The code does what the criteria say.
Validation
The criteria match what users need. A person decides.
Oracle
Decides pass or fail by checking against set rules or guidelines.

PRINCIPLES15 / 52

Six principles

The agents that write the code should not determine when work is done.

  • 1Objective criteria before the work
  • 2The author is not the judge
  • 3Deterministic checks before model judgment
  • 4Verify in a running environment on the platform that changed
  • 5Completion requires saved evidence
  • 6A person approves the criteria and the consequential steps

APPLYING VERIFICATION17 / 52

Objective acceptance criteria

An objective criterion names

  • the actor and the starting state
  • one action
  • the result, on screen and in stored state
  • a numeric threshold where one applies
  • the oracle type
  • which dependencies must be real

APPLYING VERIFICATION19 / 52

Prompt: write the criteria first

Before writing any code, write the acceptance criteria for this change as a numbered list. Each criterion must be observable from outside the code: the starting state, the action, and the expected result. Add a numeric threshold where one applies. Mark which criteria need a real service, a browser, or a device to check. Then stop and wait for my review. Do not create or edit tests or code until I approve the list.

APPLYING VERIFICATION22 / 52

Prompt: propose the test contract

For each approved criterion, propose how it will be checked: the test level (unit, integration, or end to end), the oracle (example, property, invariant, contract, approved snapshot, or comparison with a reference), and the real service or environment it runs against. Use no mocks, stubs, or fakes. If a criterion cannot be checked against a real service, stop and tell me why instead of mocking it. Wait for my approval.

Prompt: one behavior at a time

Implement this in vertical slices. For each behavior, write one test, run it, and show me that it fails for the expected reason. Then write the minimum code to make it pass and run the full suite. LIVE BUILD33 / 52

Prompt: a check in code after every workflow stage

Write an Atomic workflow for this job. Every stage writes its output to a file. After each stage, run a check in code that fails the stage when the output is missing or wrong, and send the failure output back to that stage to fix. The stage that builds something does not check it. Promote output only after its checks pass, and save a record of every check that ran.

Oracles that are harder to game

OracleHow it worksWhy it is harder to gameExample
Property-basedA rule over many generated inputsA hard-coded output can’t pass them allevery row of obstacles leaves a lane the player can pass
MetamorphicRelated inputs, related outputsNo stored expected value to copythe same inputs at 30 and 120 fps give the same score
DifferentialTwo implementations, same inputThe reference is outside the agent’s diffBlender and three.js report the same triangle count
MutationSmall faults planted in the changeCatches tests that assert nothingremove the collision check and the crash test fails
Approved snapshotA reviewed expected outputUpdating it is a person’s decisiona Blender preview render a person approved
Invariants and contractsPre- and postconditions on every runThey hold in every test and every runthe player is always in one of three lanes
Deterministic simulation and replaySeeded inputs, replayed exactlyA failure reproduces from its seeda recorded input trace replays to the same crash frame
APPLYING VERIFICATION35 / 52

Qualities of an oracle that is hard to game

  • ✓written from the criteria or a reference
  • ✓generated or relational inputs
  • ✓reproduces from a seed or a trace
  • ✓fails when the change is reverted
  • ✓outside the agent’s write access
  • ✓changes only through a reviewed diff
APPLYING VERIFICATION36 / 52

Prompt: invariants as property tests

List the invariants this module must hold for any valid input, for example round trip, idempotence, ordering, conservation of totals, or no negative balances. Write each one as a property-based test with a fixed seed. When a property fails, show me the shrunk counterexample before you change any code.

APPLYING VERIFICATION38 / 52

Prompt: review in a fresh context

You did not write this change. Review the diff against the approved acceptance criteria only. For each criterion, say whether the diff and its tests prove it, with file and line. List every test that was modified or deleted, every assertion that was removed, every snapshot that was updated, and every test that was skipped. Return findings, not fixes.

Checks on every generated 3D model

  1. Loads in three.js GLTFLoaderthe same loader the game uses, zero errors

LIVE BUILD40 / 52

Prompt: check every generated asset

Before any generated asset is used, check it. Load it with the same loader the app uses and fail on any error. Check its file size and triangle count against the budget. Render a preview from the front, side and top, and save the renders with the numbers. Mark the asset unverified until those checks pass and a reviewer has looked at the renders.
